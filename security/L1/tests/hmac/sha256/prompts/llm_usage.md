# 大模型使用随记

以下记录整理自 2025-10-31 当日对第 1 题 HMAC-SHA256 baseline 的迭代过程，主要梳理我与 VS Code 内置的 GitHub Copilot（GPT-4 引擎）之间的交互内容、采纳结果以及后续验证情况，便于评审方了解模型介入的实际作用范围。

## 一、背景与目的

- 工作内容：对 `security/L1/tests/hmac/sha256/` 中的 baseline 进行性能调优，确保在评分细则限定的约束下获得稳定的时序表现。
- 目标约束：目标时钟周期不超过 20ns，Slack 保持正值以避免扣分，Cosim latency 希望在功能正确的前提下进一步压缩。
- 开发环境：Vitis HLS 2024.2，目标器件为 xc7z020-clg484-1（Zynq-7020），已有 baseline 指标为 Estimated Clock 13.846ns、Cosim Latency 809 cycles。
- 使用动机：在限定时间内快速确认可行的 pragma 调整方案，并核实工具版本升级带来的接口变化。

## 二、主要交互：时序与延迟调优

### 1. 提示内容

我向 Copilot 提供了以下信息：

- 作业路径与题目描述，指明本次修改集中于 SHA-256 测试用例；
- 当前综合指标与评分公式，强调执行时间 = Clock × Latency，Slack 计算方式，以及扣分规则；
- 专门说明工具版本、板卡型号和优化目标，例如“CLKP 不超过 20ns”“latency 尽量降低”等。

### 2. Copilot 输出的建议概要

模型在收到上述上下文后，返回的核心建议包括：

1. 将 `run_hls.tcl` 中的 `CLKP` 调整为 19ns，以便给 Slack 留出一定余量；
2. 将 SHA-256 主循环中的 round 函数直接内联，移除 `#pragma HLS latency min=1 max=1`，并利用循环索引更新 W 数组；
3. 取消 `W[16]` 的 `bind_storage` 声明，全部展开为寄存器以减少访问延迟；
4. 将 `blk_strm`、`nblk_strm` 与 `end_nblk_strm` 的 FIFO 深度调小至个位数，从而降低缓存开销；
5. 其他备选方案（例如大规模 UNROLL 或将目标时钟设到 15ns 以下）仅作为补充结论。

### 3. 人工采纳与调整

我逐项评估这些建议，最终采纳情况如下：

- **时钟设置**：`run_hls.tcl` 中 `set CLKP 19.0` 被确认为合适，“19ns × 0.9” 的 Slack 计算方式满足评分规则，因此直接保留。
- **主循环改写**：`sha224_256.hpp` 的 64 轮循环重新组织，将原先的函数调用内联，同时删除 latency pragma 并改用更清晰的下标转换写法；此举可减轻额外的函数展开开销。
- **W 数组实现**：保留 `#pragma HLS array_partition variable=W complete`，但移除 LUTRAM 绑定，让合成工具自行使用寄存器实现，以换取更低的单周期延迟。
- **流式通道深度**：按建议将三个流的深度收窄，经过 csim 与 cosim 验证，数据流未出现阻塞或丢包，因此将改动写入代码库。

对于模型提到的“完全 UNROLL 64 轮”以及“进一步将目标时钟压低”，我在评估资源占用与时序风险后予以否决，这部分没有落地。

### 4. 验证与记录

上述改动提交前均经过以下检查：

- C 仿真与协同仿真对照 baseline，确认功能结果一致；
- 复核 `csynth.xml` 里的 Estimated Clock 以及资源使用，确保没有超出 Zynq-7020 的资源阈值；
- 在 `第1题报告.md` 中记录发生的参数调整和验证结果，保持文档一致性。

## 三、辅助交互：TCL 接口兼容性

### 1. 问题描述

在执行 `run_hls.tcl` 时，Vitis HLS 2024.2 抛出 `config_interface: Unknown option '-m_axi_alignment=64'`。我判断这是 API 变更所致，但需要确认替代参数。

### 2. Copilot 回应

我给出的 prompt 仅包含报错信息、工具版本与涉及的命令行片段。Copilot 返回的结论是：新版 API 将 `-m_axi_alignment` 重命名为 `-m_axi_alignment_byte_size`。

### 3. 处理结果

我对照 UG1399（2024.2 版）验证该说法准确无误，随后将脚本中的参数更新为新名称。再次执行流程后，报错消失，功能正常。

## 四、后续复盘与思考

1. **效率收益**：Copilot 对熟悉的 HLS 场景给出了较为具体的 pragma 组合，减少了我反复尝试的时间。尤其在循环结构和存储绑定方面，提示比较贴合经验结论。
2. **人工把关**：尽管采纳了部分建议，但所有改动都在本地重新综合与仿真验证，并结合资源评估作出取舍，避免直接照搬可能造成时序或资源风险的方案。
3. **风控意识**：对于模型提出的激进策略（如全展开或更高频），在没有充分数据支撑时仍保持谨慎，这一点在后续的报告和提交物中均有体现。
4. **记录补充**：若后续综合结果出现偏差或新增优化回合，我会继续在本文件下方补充说明，确保大模型使用痕迹与项目状态同步。
